# 实现、评测与交付约定

适用于本仓库的功能修复、模型评测及交付；用户明确给定的范围与授权优先。

## 1. 开始与定位

- 先核实工作树绝对路径、分支、基线提交及用户改动。对用户提供的命令包含实际工作树的完整切换路径。
- 当前任务只维护一个状态入口：当前版本、未解决缺陷、已验收范围、授权余额、下一动作。历史报告链接保留。
- 每次失败先记录：错误事实、所在层（模型／应用处理／展示／修正／保存）、最小复现和修复判据。
  同类失败再次出现先重查诊断，开发中已知缺陷由工程侧修复后再交用户验收。

## 2. 开发完成条件

- 沿用Issue #1的公开应用服务、真实临时SQLite及QML边界；工具自身通过公开CLI验证。
  仅替换外部HTTP、凭据、时间等边界；生产功能改动用失败记录先复现再修复。
- 修改字段后，继续编辑其他字段、选依据、重复提交、保存及重启，原修正和待核对状态须保持。
- 在工作树运行 `uv run python tools/check.py`。本地与CI共用该入口；失败退出码非零。
  CI不配置DeepSeek凭据，使用offscreen Qt；这是离线行为验证，不是模型质量评测。
- 审查时分别核对规范与需求，引用须支持完整含义；文字存在不等于语义正确。

## 3. 模型评测完成条件

- 使用现有 `docs/evaluation/capture_issue12_candidate.py`，先省略`--run`生成执行计划。
  冻结完整候选SHA、提示词、样例、契约示例和执行代码；开发模式只使用调优位置。
- `contract-examples.json`覆盖明确日期、歧义和缺失日期；检查字段完整性及应用结构。
  同候选开发响应也要过契约检查。结构通过不证明模型理解正确。
- 正式计划须传`--development-review`；评审文件逐轮绑定同候选、提示词及原始采集，
  `raw_file`指向评测目录中的开发记录，`raw_lf_sha256`用统一LF计算；
  `unresolved_defects`须明确为空，`runs`完整列出`case/trial/reviewer/passed_agent_review/errors`。
  评审结论由代理实际逐项核对后填写，不能由工具自动宣称语义通过；报告注明本次覆盖的开发范围。
- 正式运行前扫描全部历史采集：有过HTTP尝试的保留ID或同原文不能再冒充未调用保留样例。
  继续使用已消耗样例做开发允许；首次保留检验在开发完成、候选固定后执行。
- 新增真实调用先说明发送内容、轮次、重试与用量，取得明确授权；开发预算与停止条件可提前一起约定。
  由代理记录`--authorization`文件，格式为`{"approval_reference":"用户授权所在消息","plan":执行计划对象}`。
  文件须逐项匹配干运行输出的`execution_plan`，不替代真实授权，不让用户手写JSON。
  再以相同参数加`--authorization 路径 --run`执行；离线检查环境始终禁止真实调用。
- 所有输出、失败和尝试均保留；不挑选补跑、不改旧评分。原始模型、应用草稿、行为测试和用户验收分开报告。
  历史冻结协议与旧报告保持原状；新工具约束用于后续计划，不回填历史通过状态。

## 4. 用户验收与收尾

- 一个准确入口；每项写“操作—预期—反馈”。产品含义与界面操作分别验收，已通过项目保持有效。
- 用户只判断可用性和确需其决定的产品歧义；已知缺陷的定位、评分与修复由工程侧承担。
- 更新只包含：当前结论、剩余问题、下一动作、是否需要用户操作。提交与历史明细放报告。
- 已授权的修复、检查和审查持续推进；外发调用、合并、关闭等边界在最终交付包中一次列清，按实际授权执行。
- PR附验证、验收范围及限制。CI工作流通过不等于强制门禁：仓库管理员需将
  `Offline checks (Windows)`设为main的必需检查；未设置时如实报告，不称已强制拦截合并。
